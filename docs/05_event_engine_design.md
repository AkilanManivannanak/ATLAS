# Deterministic event engine — Phase 2

## Contract and ordering version

The engine uses `atlas-event-order-v1`. Event ordering is the tuple:

```text
(scheduled_at, phase_priority, insertion_order, event_id)
```

`event_id` is a final defensive tie-breaker; insertion order is unique for successfully scheduled events. For the same timestamp, the versioned phases are:

| Priority | Phase |
|---:|---|
| 10 | Payment-system state changes |
| 20 | Funding and collateral changes |
| 30 | Payment arrivals |
| 40 | Eligibility and queue processing |
| 50 | Settlement |
| 60 | Participant decisions |
| 70 | Monitoring and snapshots |

This is a simulator convention, not a statement about a real payment network. Changing this order requires a new version and new replay fixtures. Handlers cannot schedule an event earlier than the current event's phase at the same timestamp.

## Clock and queue semantics

The simulation begins at a configured timezone-aware start. `run_until(t)` processes events scheduled at or before `t` (inclusive), then advances the simulation clock to `t`. The clock cannot move backward. Events in the past and duplicate event identifiers are rejected. Pending events may be cancelled; applied or cancelled events cannot be cancelled again.

## Handler contract and failure behavior

Handlers receive a JSON state copy, the immutable event, and an `EventContext`. A handler returns the next JSON-object state. State and event payloads reject floating-point values to protect authoritative state from binary-float ambiguity.

Handlers must be deterministic, perform no I/O, and use only named context random streams. Event state, context random draws, and events staged by a handler commit together only after successful return and validation. On handler failure, state, newly scheduled events, and staged random draws are discarded; the engine records the failing event and halts. Recovery is from a prior snapshot, not an implicit retry.

## Reproducibility

`SimulationConfig` pins simulation ID, aware start time, master seed, event ordering version, and handler version. Named independent streams use a stable SplitMix64 integer generator seeded from SHA-256 of the master seed and stream name. Event handlers do not share or consume one global random sequence.

Replay starts from the same initial state and configuration and receives the same initial scheduled event stream with recorded insertion orders. Dynamic events are regenerated by versioned deterministic handlers. A state digest supports direct replay comparisons.

## Snapshots

A snapshot contains the current and initial states, SHA-256 state digest, pending/cancelled/applied event records, known event IDs, next insertion order, clock, configuration versions, and all named random stream states. Snapshots round-trip through canonical JSON, can be validated, and can restore the engine with a compatible handler set.

## Current limits

The engine is in-memory; it has no durable event store, multi-day business calendar, rail adapters, database checkpoint persistence, distributed processing, or performance benchmark. Replay verifies deterministic state under the same handler implementation/version; it does not yet provide cross-version migration.
